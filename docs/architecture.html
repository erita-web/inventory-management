Overview

A full-stack demo built for a Claude Code workshop. A Vue 3 single-page app talks over HTTP/JSON to a FastAPI backend, which serves sample factory data (inventory, orders, demand, backlog, spending) held in memory. There is no database: the sample data is read-only and reloads on every server restart. The one exception is restock orders, which are saved to a small JSON file so they survive restarts.

System architecture

Three parts: the browser app, the API server, and the JSON files it loads. The browser only ever talks to the API; it never reads the data files directly.

Data flow

Two flows matter: what happens once when the server starts, and what happens each time a page loads or a filter changes.

1. At server startup

Read
mock_data.py opens each file in server/data/ and parses it with json.load.
Hold
Each dataset becomes a module-level Python list (orders, inventory_items, …).
Serve
main.py imports those lists and filters them per request. Edits to the JSON need a restart.

2. When a page loads or a filter changes (Dashboard example)

  1. The user picks a filterFilterBar offers Period, Warehouse, Category and Order status. It writes to shared refs in useFilters, a module-level singleton that every view reads.
  2. The view noticesEach data view loads on mount and re-loads through a watch() on those refs.views/Dashboard.vue → watch([selectedPeriod, selectedLocation, selectedCategory, selectedStatus])
  3. The API client builds the querygetCurrentFilters() returns {warehouse, category, status, month}. api.js drops any value equal to 'all' and appends the rest as a query string.
  4. Requests go out in parallelThe Dashboard calls /dashboard/summary, /orders, /inventory and /backlog together with Promise.all.
  5. FastAPI filters the in-memory listsapply_filters matches warehouse exactly and category/status case-insensitively. filter_by_month does a substring match on order_date; a value like Q1-2025 expands to its three months.
  6. The server shapes the responsePydantic response_models validate list endpoints. The summary endpoint computes its totals on the server: inventory value = Σ quantity × unit cost; low stock = quantity ≤ reorder point; pending = Processing + Backordered orders.
  7. The view derives what it showsRaw results land in refs (allOrders, inventoryItems); computed properties turn them into chart series, KPIs and top products. formatCurrency converts USD to JPY at a fixed 150 rate when the language is Japanese.

3. When a restock order is placed

Submit
The Restocking page sends only the budget (POST /api/restocking/orders). The server rebuilds the recommendation itself, so prices and quantities can't be changed from the browser.
Save
The order's lead time is its slowest item's lead time. It is written to server/data/restock_orders.json (gitignored) before being kept in memory, so the file and memory never disagree.
Show
The Orders page loads GET /api/restocking/orders separately from the filtered customer orders and lists them in a Submitted Orders section, with lead time and expected delivery.
Good to know: the inventory endpoints have no date field, so the Period filter never affects inventory data. api.js only forwards warehouse and category for inventory. Language is stored in localStorage (app-locale) and currency follows it (English = USD, Japanese = JPY).

Gaps & quirks to know before building

Things found while reading the code. Several look like features that were started but not finished, which may be intentional for a workshop.

The frontend calls 6 routes the backend does not have

Tasks (GET/POST /tasks, DELETE/PATCH /tasks/{id}) and purchase orders (POST /purchase-orders, GET /purchase-orders/{id}) are defined in the API client but not in main.py. The task load fails quietly (logged to the console) and the mock tasks from useAuth still show.

client/src/api.js:77-105 · client/src/App.vue (loadTasks)
The purchase-order feature is half-built

Pydantic models exist and purchase_orders.json is an empty list. Dashboard.vue renders a <PurchaseOrderModal> that is never imported and has no file, so Vue cannot resolve it. The backlog template checks item.purchase_order_id, but the API returns has_purchase_order.

client/src/views/Dashboard.vue:213, :289, :305-313 · server/main.py (PurchaseOrder models)
Some Dashboard KPIs are hard-coded

Orders fulfilled (187 of a 200 goal) and fill rate (96.8%) are constants, not calculated from the API.

client/src/views/Dashboard.vue:340-341
One page is unreachable, and one ignores the filters

Backlog.vue has no route and is not imported anywhere. Reports.vue does not use useFilters and calls the API with its own hard-coded URL instead of api.js.

client/src/main.js · client/src/views/Reports.vue:156-162
Quarter and date logic is duplicated and string-based

filter_by_month uses a QUARTER_MAP, while the quarterly report repeats the quarters as chained '2025-01' in order_date checks. Both match on substrings of the date and only know 2025.

server/main.py:10-31, :230-274
Open by design for local use

No authentication, CORS allows every origin (with credentials), the server binds to all network interfaces, and the API address localhost:8001 is hard-coded in the client (in api.js and twice in Reports.vue).

server/main.py:49-56, :309
Documentation has drifted from the code

tests/TEST_SUMMARY.md still lists an "Orders Endpoints (15 tests)" suite, but there is no orders test file. mock_data.py says the data is from September 2025, but orders span all of 2025. generate_data.py only writes orders.json and its product catalog (Widgets, Components…) does not match the categories in the shipped data, so it is not how the current data was made.
